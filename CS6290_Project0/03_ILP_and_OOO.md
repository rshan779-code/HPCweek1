## 1. 指令级并行（ILP）

**ILP** = 程序中理论上可以同时执行的指令数量

### 为什么需要 ILP？

```
目标：CPI < 1（每周期执行多条指令）

超标量处理器：每周期发射/执行 2-6 条指令
→ 理论 IPC = 发射宽度（如 4-wide = IPC 最高 4）
→ 实际 IPC 受各种依赖和冒险限制
```

---

## 2. 三种数据依赖

| 类型 | 名称 | 示例 | 是否真依赖 |
|------|------|------|-----------|
| **RAW** | Read After Write（写后读）| I1 写 R1，I2 读 R1 | ✅ 真依赖，必须保序 |
| **WAW** | Write After Write（写后写）| I1 写 R1，I3 写 R1 | ❌ 假依赖，可消除 |
| **WAR** | Write After Read（读后写）| I2 读 R1，I3 写 R1 | ❌ 假依赖，可消除 |

### 举例说明

```asm
I1: ADD R1, R2, R3    # 写 R1
I2: SUB R4, R1, R5    # 读 R1 ← RAW（真依赖，I2 必须等 I1）
I3: MUL R1, R6, R7    # 写 R1 ← WAW 与I1（假），WAR 与I2（假）
```

**消除假依赖 → 寄存器重命名！**

## 3. 寄存器重命名（Register Renaming）

### 原理

把 ISA 的逻辑寄存器（如 32个）映射到更多的**物理寄存器**（如 192个）

```
逻辑寄存器（程序看到的）：R0-R31（32个）
物理寄存器（硬件实际有）：P0-P191（192个）
RAT（Register Alias Table）：记录当前 R0-R31 分别对应哪个物理寄存器
```

### 例子

```asm
# 原程序（有假依赖）：
I1: ADD R1, R2, R3   # WAW：I1 和 I3 都写 R1
I2: SUB R4, R1, R5   # WAR：I2 读 R1，I3 写 R1
I3: MUL R1, R6, R7
I4: ADD R4, R1, R8   # 读 I3 写的 R1

# 重命名后（假依赖消除）：
I1: ADD P10, P2, P3   # R1 → P10
I2: SUB P11, P10, P5  # R1 读 P10，R4 → P11
I3: MUL P12, P6, P7   # R1 重新映射 → P12（与P10不同！）
I4: ADD P13, P12, P8  # 读 I3 的结果 P12
```

消除了 WAW（I1/I3）和 WAR（I2/I3）！I3 可以提前执行，不必等 I2。

## 4. 乱序执行（Out-of-Order Execution）

### 基本流程

```
顺序取指 → 顺序解码 → 顺序发射到保留站
       → 乱序执行（操作数就绪就执行）
       → 乱序完成
       → 顺序提交（ROB 保证）
```

### Tomasulo 算法

**保留站（Reservation Station, RS）**：
- 每个执行单元（ALU、FP、Load/Store）有自己的 RS
- 保存等待执行的指令 + 操作数（或等待哪个结果）

```
RS 表项结构：
  | Op | Vj | Vk | Qj | Qk | A  | Busy |
  操作  值1  值2  等待1 等待2 地址  是否占用

Vj/Vk: 操作数值（若已就绪）
Qj/Qk: 等待哪个 RS 的结果（若未就绪）
```

**执行流程**：

```
1. Issue（发射）：
   - 把指令放入 RS
   - 查 RAT：操作数就绪 → 填 V；未就绪 → 填 Q（等哪个 RS）

2. Execute（执行）：
   - 当 Qj=0 且 Qk=0（两个操作数都就绪）→ 开始执行

3. Write Result（写结果）：
   - 结果通过 CDB（公共数据总线）广播
   - 所有 RS 监听 CDB，若 Q 匹配 → 把结果填入 V，清除 Q
```

## 5. ⭐ 重排序缓冲（ROB - ReOrder Buffer）

### 为什么需要 ROB？

Tomasulo 算法乱序 commit，导致：
1. **精确异常失败**：异常发生时无法确定"哪些指令已执行"
2. **分支恢复困难**：无法撤销已 commit 的错误指令

### ROB 原理

```
所有指令按程序顺序进入 ROB
指令可乱序执行，但必须按 ROB 顺序（程序顺序）commit
只有 commit 才真正修改架构状态（寄存器/内存）
```

```
ROB 结构（环形队列）：

Head → [I1: ADD, P10, Done, 结果=25]   ← 最老，等待 commit
       [I2: LW,  P11, Done, 结果=100]
       [I3: MUL, P12, Done, 结果=50]
       [I4: BEQ, ---, Done, 跳转=否]
Tail → [I5: SUB, P13, 执行中, --]      ← 最新
```

**Commit 规则**：
- Head 指向的指令完成 → commit，写入真实寄存器，Head 前进
- Head 指向的指令未完成 → 等待（即使后面的都完成了）

### 精确异常处理

```
场景：I3 执行时发生除零异常

ROB 状态：
  [I1: Done]  ← 已 commit
  [I2: Done]  ← 已 commit
  [I3: 异常]  ← 异常在这里，等待轮到它 commit
  [I4: Done]  ← 执行完了，但不能 commit（I3 还没提交）
  [I5: 执行中]

处理：
  等 I3 到达 ROB Head → commit 时触发异常 handler
  Flush ROB 中 I3 之后的所有指令（I4, I5...）
  跳转到异常处理程序
  恢复时从 I3 之后重新开始
```

### 分支预测错误恢复

```
场景：I4 是分支指令，预测"不跳"但实际"跳"

ROB：
  [I1: Done]  
  [I2: Done]
  [I3: Done]
  [I4: BEQ, 预测错误！] ← 到达 Head 时发现预测错
  [I5: ADD, 在错误路径上] ← Flush！
  [I6: MUL, 在错误路径上] ← Flush！

动作：
  1. Flush ROB 中 I4 之后的所有指令
  2. 恢复 RAT 到 I4 之前的状态（用 ROB 中存的旧映射）
  3. 从正确的分支目标地址重新取指
```

## 6. 超标量处理器关键数字

| 参数 | 典型值 | 作用 |
|------|--------|------|
| 发射宽度 | 3-6 条/周期 | 每周期最多发射几条 |
| ROB 大小 | 100-300 项 | 乱序窗口大小 |
| 保留站数量 | 20-100 项 | 等待执行的指令数 |
| 物理寄存器数 | 128-256 个 | 支持寄存器重命名 |
| 执行端口数 | 4-8 个 | 同时能执行几条 |

**Intel Core i9（Skylake）**：
```
发射宽度：4
ROB：224 项
物理寄存器：180 整数 + 168 浮点
执行端口：8 个
```

## 7. ILP 与分支预测的关系

乱序窗口越大（ROB 越大）→ 能"看到"更多指令 → 发现更多 ILP

**但**：遇到分支，乱序窗口被"卡住"：

```
ROB:
  [I1: ALU, Done]
  [I2: LOAD, Done]
  [I3: BEQ, 预测跳...]   ← 在等待确认
  [I4: ADD, Done]        ← 预测路径上的指令
  [I5: MUL, Done]        ← 预测路径上的指令
  [I6: ...]
  
I3 没有 commit，I4/I5 就不能 commit
如果预测错 → I4/I5 全部作废，ROB 清空 → 流水线泡沫
```

→ **分支预测越准，ROB 越能充分利用，IPC 越高**

## 8. 总结对比

| 机制 | 解决的问题 | 关键数据结构 |
|------|-----------|------------|
| 寄存器重命名 | 消除 WAW/WAR 假依赖 | RAT（寄存器别名表） |
| 保留站 | 等待操作数就绪再执行 | RS + CDB |
| ROB | 精确异常 + 顺序 commit | 环形队列 |
| BTB + 分支预测 | 减少控制冒险 | BHT/PHT + BTB |
